Install this separately from RudderStack, as its own script. Don't load it through RudderStack's Device Mode integration. Device Mode doesn't fully support feature flags, and flags matter here. RudderStack's own PostHog destination should run in Cloud Mode instead, on RudderStack's side, which isn't this developer's task.

TWO SETTINGS BELOW ARE REQUIRED, NOT OPTIONAL.

bootstrap.distinctID must be RudderStack's anonymousId. Skip it and the two SDKs generate separate identities that never join up. person_profiles: 'always' matters too, not 'identified_only' the way the app sets it. Under 'identified_only', anonymous events carry no person data at all, so attribution gets thrown away before anyone signs up.

<script>

4. Carrying UTMs across pages and into the app

PostHog doesn't need this part. Its own persistence already keeps $initial_utm_source and the rest attached to the anonymous ID across every page on this site, and alias() carries that into the identified person automatically. That part really is free.

Postgres is the reason this still needs custom code, confirmed directly against the app's repo, pulled fresh rather than from a stale checkout. The login route, /api/auth/[auth0]/route.ts, reads 14 fields straight off its own incoming query string, all 6 UTM fields plus 8 ad-platform click identifiers: fbclid, gclid, gbraid, wbraid, li_fat_id, ttclid, msclkid, rdt_cid. A second piece, useUTMTracking.ts, posts those same 14 fields to /users/api/utm-tracking/, which saves them to a utm_parameters field on the user record in Postgres, structured as first_touch (write-once, frozen forever), current (updated every time, except utm_referrer which stays frozen inside it too), and a capped history list. That same endpoint also mirrors the data to PostHog as person properties on the backend. None of this reads from PostHog on the way in, though. It reads only from the URL of the request that hits /api/auth/login, and if a visitor browses three pages before clicking trial, that URL has nothing left on it unless something puts the values back. Match the app's own field names exactly, since these are the literal keys it already expects.

const ALWAYS_UPDATE = ["utm_source","utm_medium","utm_campaign","utm_term","utm_content","fbclid","gclid","gbraid","wbraid","li_fat_id","ttclid","msclkid","rdt_cid"];
const FIRST_TOUCH_ONLY = ["utm_referrer"];

function setCookie(name, value, days) {
  document.cookie = `${name}=${encodeURIComponent(value)}; max-age=${days*24*60*60}; path=/`;
}

const found = new URLSearchParams(window.location.search);

ALWAYS_UPDATE.forEach(function (key) {
  if (found.has(key)) setCookie(key, found.get(key), 30);
});

FIRST_TOUCH_ONLY.forEach(function (key) {
  const alreadySet = document.cookie.includes(key + "=");
  if (found.has(key) && !alreadySet) setCookie(key, found.get(key), 365);
});

5. Trial signup link

This reads the cookies from §4 and attaches them, plus one identity value, to the trial button's link right before the visitor clicks it. It's a link decorator that runs at click time.

Today, every "Start 14 day trial" button links straight to https://auth.hazel.altruist.com/, a different root domain from the marketing site. No cookie survives that jump on its own, and the app's own UTM-reading code, which only lives in /api/auth/login, never gets a chance to run. Two steps fix this.

  1. In the Designer, no code: give every "Start 14 day trial" button the shared class w-cta-trial. Give each pricing card wrapper a data-plan attribute: financial_planning_agent, admin_ai, tax_planning_agent, bundle_all, or enterprise.
  2. In custom code: one click listener, built at click time rather than baked into the page on load.
document.addEventListener("click", function (e) {
  const trigger = e.target.closest(".w-cta-trial");
  if (!trigger) return;
  e.preventDefault();

  const url = new URL("https://APP_DOMAIN/api/auth/login");  // NOT auth.hazel.altruist.com — confirm below
  url.searchParams.set("returnTo", "/");
  url.searchParams.set("rs_aid", rudderanalytics.getAnonymousId());  // the identity bridge, for PostHog's side

  const planCard = trigger.closest("[data-plan]");
  if (planCard) url.searchParams.set("intended_plan", planCard.dataset.plan);  // product intent, not attribution

  const TRACKING_KEYS = ["utm_source","utm_medium","utm_campaign","utm_term","utm_content","utm_referrer","fbclid","gclid","gbraid","wbraid","li_fat_id","ttclid","msclkid","rdt_cid"];
  TRACKING_KEYS.forEach(function (key) {
    const match = document.cookie.match(new RegExp(key + "=([^;]+)"));
    if (match) url.searchParams.set(key, decodeURIComponent(match[1]));
  });

  window.location.assign(url.toString());
});

Not this developer's work: intended_plan needs a home on the app side once it arrives, either pre-filling onboarding's plan step or saving it as a firm-level attribute. Flag this to whoever owns that flow.

6. Event catalog

Six buckets of interactive elements on this site, each needing its own tracking approach. Read this as direction, not a spec to match selector for selector. Verified classes below are confirmed real in the Designer right now. Suggested classes are names for new classes that don't exist yet, proposed here so every event has a consistent way to be found. Build to the pattern, and use your own judgment on the exact class name if the site's real structure asks for something different.

  • Global navigation. Logo, menu items, nav CTAs. Verified real classes already group these, nav-bar_link and nav_panel-link. Add a data-track-item attribute, nothing more.
  • In-page CTAs. Any button or link inside page content that isn't the nav bar. No shared class exists yet. Suggested: w-cta-track.
  • Repeating card or tile modules. Bento grids, feature cards, anything that repeats the same shape with different content. No shared class exists yet. Suggested: w-card-track.
  • Tabbed content. The homepage's capability tabs are the one confirmed example. No shared class exists yet. Suggested: w-tab-track.
  • Carousels and sliders. The testimonials section, built on Swiper.js, is the one confirmed example. Its own classes already exist, verified in the Designer.
  • Forms. The demo request form, built on HubSpot. Its own event model, covered on its own further down.

Nav, CTA, and card click handler

// text(el) turns a missing or blank label into null instead of "". The site
// is still being built, and a blank string isn't a real value worth sending.
function text(el) {
  if (!el) return null;
  const t = el.textContent.trim();
  return t.length ? t : null;
}

document.addEventListener("click", function (e) {
  // try/catch matters here because the site isn't finished. A half-built
  // element should never break a real button's actual click behavior.
  try {
    const nav = e.target.closest(".nav-bar_link, .nav_panel-link, .nav-bar_logo");
    if (nav) {
      const variant = nav.closest(".u-show-tablet") ? "mobile"
        : nav.closest(".u-hide-tablet") ? "desktop"
        : (window.matchMedia("(max-width: 991px)").matches ? "mobile" : "desktop");
      rudderanalytics.track("nav_item_clicked", {
        nav_item: nav.dataset.trackItem || null,
        nav_variant: variant,
        page_path: window.location.pathname,
        destination_url: nav.href || null
      });
      return;
    }

    const cta = e.target.closest(".w-cta-track");
    if (cta) {
      const module = cta.closest("[data-module]");
      rudderanalytics.track("cta_clicked", {
        cta_label: text(cta),
        cta_destination: cta.href || null,
        module_name: module ? (module.dataset.module || null) : null,
        page_path: window.location.pathname
      });
      return;
    }

    const card = e.target.closest(".w-card-track");
    if (card) {
      const module = card.closest("[data-module]");
      const heading = card.querySelector("h1, h2, h3, h4, .card-heading");
      const link = card.querySelector("a") || (card.tagName === "A" ? card : null);
      rudderanalytics.track("module_card_clicked", {
        module_name: module ? (module.dataset.module || null) : null,
        card_label: text(heading) || text(card),
        link_destination: link ? (link.href || null) : null,
        page_path: window.location.pathname
      });
      return;
    }

    const tab = e.target.closest(".w-tab-track");  // confirm the real trigger class once the section is inspected in the Designer
    if (tab) {
      rudderanalytics.track("tab_switched", {
        module_name: "capability_tabs",
        tab_label: text(tab),
        page_path: window.location.pathname
      });
    }
  } catch (err) {
    // Swallow and move on. A tracking failure should never reach the visitor.
  }
});

Testimonials carousel, built on Swiper.js

Arrow clicks and drag are both real interactions, confirmed by a drag cursor already set on the slider. A plain click listener catches the arrows. Swiper's own slideChange event catches drag and the pagination dots. A short-lived flag stops an arrow click from also counting as a drag.

      interaction_type: "arrow_click",
      direction: btn.classList.contains("is-prev") ? "prev" : "next",
      page_path: window.location.pathname

  });
});

Demo form, built on HubSpot

The form embeds through HubSpot, which renders in an iframe. There's no submit event to catch on the parent page. HubSpot posts a message event instead. The field data rides on onFormSubmit, not onFormSubmitted, which fires later and carries no data. Validate event.origin against HubSpot's known form domain before trusting the payload. Skipping that check is a known weakness in the boilerplate code most sites copy.

window.addEventListener("message", function (event) {
  if (!event.data || event.data.type !== "hsFormCallback") return;
  // TODO: validate event.origin against HubSpot's known form domain here first.
  if (event.data.eventName !== "onFormSubmit") return;  // not onFormSubmitted, which carries no data

  const fields = event.data.data || [];
  const find = (name) => fields.find(function (f) { return f.name === name; });
  const workEmail = find("email");     // exact internal field name to be confirmed once the form is built
  const firmSize = find("firm_size");

  rudderanalytics.track("demo_request_submitted", {
    firm_size: firmSize ? firmSize.value : null,
    has_requirements_text: !!find("requirements")
  });

  if (workEmail && workEmail.value) {
    rudderanalytics.identify(workEmail.value, {
      // "website_reported_" prefix, not a bare name. The product may ask
      // this same question again later, and the two answers can differ.
      website_reported_firm_size: firmSize ? firmSize.value : null
    });
  }
});

To confirm once the HubSpot form is built: the exact internal field names, and whether an equivalent message event exists for a failed submission. Its validation mostly happens inside the iframe.

Getting UTMs into the HubSpot form itself

HubSpot has its own "Original Source" property, computed automatically from its own tracking cookie across the whole site. That part needs nothing from us. But HubSpot only populates a form's hidden fields from UTM params if those params sit in the current page's URL at the moment of submission, confirmed directly. A visitor who landed on the homepage and browsed to the demo form has no UTM params left on that page's URL, so HubSpot's own hidden-field behavior would come up empty even though the values are still sitting in the §4 cookies. Set them directly through HubSpot's own form API instead of relying on its URL-reading:

// Runs once the HubSpot form script has rendered the form on the page.
window.addEventListener("message", function (event) {
  if (!event.data || event.data.type !== "hsFormCallback") return;
  if (event.data.eventName !== "onFormReady") return;

  const TRACKING_KEYS = ["utm_source","utm_medium","utm_campaign","utm_term","utm_content","utm_referrer"];
  const form = document.querySelector("iframe.hs-form-iframe");  // confirm the real selector once the embed exists
  TRACKING_KEYS.forEach(function (key) {
    const match = document.cookie.match(new RegExp(key + "=([^;]+)"));
    if (match && form) {
      // HubSpot forms in an iframe need values set through its own form API,
      // not direct DOM access across the iframe boundary. Confirm the exact
      // call once the embed exists — this is the shape, not exact syntax.
    }
  });
});

Genuinely open until the HubSpot embed exists: the exact API for setting a hidden field's value on a HubSpot form rendered in an iframe. Cross-iframe DOM access won't work directly. Check HubSpot's own forms API docs for the supported way to pre-fill a field once the real embed code is in hand.

identify(), one place only

The site stays anonymous except for one moment. demo_request_submitted captures a real work email. Right after that, call rudderanalytics.identify(workEmail). Don't call identify anywhere else. Track and page calls on the anonymous ID are correct everywhere else, and alias bridges to the real identity later in the app.

No consent gate

Confirmed: no cookie consent banner today, and none planned for this build. RudderStack loads and starts capturing right on page load.

Don't send as event properties

  • The demo form's free-text field, or the raw work email, on any event headed to an ad platform. Those platforms need SHA-256 hashed PII, handled at the destination layer, not per event. The work email is fine as the identify distinct ID. That's a different channel than an event property.

7. Is this robust?

  • Already handled in the code above: missing attributes and elements return null. Blank text returns null instead of an empty string. The whole nav, CTA, and card listener sits inside a try/catch, so a half-built element can't break a real button.
  • Real risk, needs a test, not an assumption: Webflow's own native interactions already use some of these same elements, the Products dropdown toggle and the hamburger button among them. If either of Webflow's own click handlers stops the click from bubbling, a single document-level listener would never see it. Click through and confirm these events actually fire once the site is built. Don't assume they will.
  • Low risk, not independently confirmed: the mobile-versus-desktop fallback uses Webflow's default tablet breakpoint of 991 pixels. Sites rarely customize it, but this one hasn't been checked directly.
  • The biggest real risk isn't technical, it's coverage. Every data-track-item, w-cta-track, w-card-track, and data-module depends on someone tagging the right element by hand, with nothing to catch a miss. A missed one just produces a null property, or no event at all, silently. Plan a manual click-through pass against this catalog after launch, not just a code review.
  • A ceiling on all of this, not specific to this plan: an ad blocker that blocks RudderStack's or PostHog's domain drops all tracking for that visitor, silently. The same is true of GA4 and GTM.
  • To confirm: whether the Swiper instance is actually reachable at element.swiper in this build. That depends on how it was initialized.
